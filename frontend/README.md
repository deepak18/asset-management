# Frontend — Asset Management Terminal

Next.js (App Router) + TypeScript dashboard for the local investment-research
platform. The browser talks to the backend **only** through the versioned REST
API — there is no shared code or DB access. The API contract
(`../backend/openapi.json`) is the single source of truth: TypeScript types are
generated from it, and the UI is built and tested against **MSW mocks** so it
never blocks on a live backend.

## Stack

| Concern | Choice |
|---|---|
| Framework | Next.js 16 (App Router, Turbopack) |
| Language | TypeScript 5 (strict, `noUncheckedIndexedAccess`, no `any`) |
| Styling | Tailwind CSS 3 + shadcn/ui-style primitives |
| Charts | Recharts (donut allocations) |
| Contract types | `openapi-typescript` → `src/types/api.ts` |
| Mock layer | MSW (`msw/node` in tests, `msw/browser` in dev) |
| Tests | Vitest + React Testing Library (jsdom) |

## Prerequisites

- **Node.js ≥ 20** (developed on 24 LTS) and npm. Install on Windows with
  `winget install OpenJS.NodeJS.LTS`.

## Setup

```powershell
cd frontend
npm install
cp .env.local.example .env.local   # then edit if your API host differs
```

`.env.local` variables:

| Variable | Purpose |
|---|---|
| `NEXT_PUBLIC_API_BASE_URL` | Backend origin (scheme + host), e.g. `http://localhost:8000`. |
| `NEXT_PUBLIC_API_MOCKING` | `enabled` → run the UI against in-browser MSW mocks; unset → call the real API. |

## Everyday commands

```powershell
npm run dev        # dev server at http://localhost:3000
npm run test       # Vitest + RTL (jsdom), MSW-mocked — no live backend needed
npm run test:watch # watch mode
npm run typecheck  # tsc --noEmit (strict)
npm run lint       # eslint (flat config)
npm run build      # production build
npm run typegen    # regenerate src/types/api.ts from ../backend/openapi.json
```

A change is **done** only when `test`, `lint`, and `typecheck` are all green.

## Mock-first, then live

The UI is developed against the contract, not a running backend:

1. **Mock mode (default for local UI work).** Set `NEXT_PUBLIC_API_MOCKING=enabled`.
   MSW intercepts every request in the browser and serves fixtures from
   `src/mocks/` shaped by the generated contract types. Tests always run this way
   (via `msw/node`), so the suite needs no backend.
2. **Live mode.** Unset `NEXT_PUBLIC_API_MOCKING` (or set it to anything else) and
   point `NEXT_PUBLIC_API_BASE_URL` at the running FastAPI server. The typed API
   client (`src/lib/api-client.ts`) is the only thing that changes behavior — the
   components don't know the difference.

**When the backend publishes a new `openapi.json`:** run `npm run typegen`,
fix any resulting type errors, then update/remove the matching MSW handler in
`src/mocks/handlers.ts` (and its fixture) as endpoints go live. The generated
`src/types/api.ts` is tool-owned — never hand-edit it.

The MSW browser worker file (`public/mockServiceWorker.js`) is generated by
`npx msw init public/ --save` and is git-ignored; re-run that once after a fresh
clone if you use browser mock mode.

## Run the full stack locally (live mode)

Live mode is the zero-config default: with no `.env.local` (or with
`NEXT_PUBLIC_API_MOCKING` unset), the client calls the real API at
`NEXT_PUBLIC_API_BASE_URL` (default `http://localhost:8000`).

```powershell
# terminal 1 — backend API (see ../backend/README.md)
cd ../backend
uv run uvicorn app.main:app --reload      # http://localhost:8000/docs

# terminal 2 — this app, live
cd frontend
npm run dev                               # http://localhost:3000
```

Both backend-side prerequisites are now in place, so live mode works end-to-end:

1. **CORS** allows the dev origin `http://localhost:3000` — the backend enables
   config-driven CORS for it, so the browser's cross-origin `GET`s go through.
2. **Portfolio id `1` is seeded** — the dashboard requests `/api/v1/portfolios/1`
   and its `/transactions`, `/holdings`, `/analytics`, and the backend serves a
   demo portfolio there. (Against an empty DB every panel renders its
   empty/error state by design — we never fake a `0`.)

## How the money model works (important)

The backend serializes all monetary/quantity/weight/rate values as **Decimal
strings** (never floats). The UI honors that end-to-end:

- `src/lib/decimal.ts` parses/rounds/scales those strings **without** `Number`
  arithmetic, so no float rounding error ever reaches a displayed figure.
- `src/lib/format.ts` renders them (`formatMoney`, `formatPercent`) and shows an
  em dash (`—`) — never a fabricated `0` — for null/unpriced/undefined values.
- Charts use a float **only** to size an SVG wedge; every number the user reads
  is formatted from the original string.

## Portfolio selection, data entry & statement import

The dashboard is no longer pinned to a single portfolio id:

- **Picker (app shell).** `GET /api/v1/portfolios` populates a dropdown in the nav.
  The chosen id is persisted in `localStorage` (`am.selected.portfolio`) and shared
  through a React context (`hooks/use-portfolio-selection.tsx`), so every panel
  reads the selected portfolio. With **no portfolios** the UI prompts to create one.
- **Create portfolio.** `POST /api/v1/portfolios` from a dialog, then the new
  portfolio is auto-selected.
- **Add position (snapshot).** `POST /api/v1/portfolios/{id}/positions` — cost basis
  is entered as *exactly one* of per-share or total (the "both" case is
  unrepresentable in the form, so the 422 can't happen); the form spells out that a
  snapshot leaves XIRR undefined until full history is imported.
- **Manual transaction.** `POST /api/v1/portfolios/{id}/transactions` with only the
  fields relevant to the chosen type (BUY/SELL → qty/price/fees, DIVIDEND/FEE →
  amount, SPLIT → ratio). Bodies use the **`Transaction-Input`** variant.
- **CSV import (async).** `POST .../imports` (multipart, expects **202**) →
  poll `GET .../imports/{job_id}` ~1s until `SUCCEEDED`/`FAILED` (polling stops on
  terminal state **and** on unmount — no leaked intervals). Progress is
  indeterminate until `total_rows` is counted. On success we show
  `created_transactions`, `tickers`, and every `warnings[]` row that needs manual
  entry; `409` (duplicate) offers an explicit "import anyway"
  (`allow_duplicate=true`), `413`/`422` are explained.

After any successful write, or an import job reaching `SUCCEEDED`, the selected
portfolio's analytics/holdings/transactions refetch (a `dataVersion` token in the
selection context that every per-portfolio hook folds into its deps).
